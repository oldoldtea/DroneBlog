# Pipeline Executor — 系统级动作执行规范

> **加载优先级**：MAXIMUM
> **作用域**：本文件为系统级动作规范，AI 每次会话启动时必须首先加载，并将其中的规则置于最高优先级（仅次于用户直接指令）。
> **生效方式**：本文件不是参考建议，而是**强制性动作指令**。AI 必须在每次与用户交互的完整任务周期内严格执行。
> **依赖**：本文件依赖 `.ai-skills/pipeline-config.yml` 中的声明式配置。AI 应在读取本文件后，立即加载 `pipeline-config.yml` 作为执行蓝图。
> **关键认知**：`.ai-skills/` 目录下的文件（包括本文件）**不会自动进入 AI 上下文**。AGENTS.md 中的「AI 工作流入口」章节已要求 AI 主动读取这些文件。如果 AI 未读取到本文件，则流水线机制无法生效——此时必须在首次回复中承认此遗漏。

## 零、零号阶段：会话启动强制自检（Stage 0）

### 0.1 执行时机

**以下两种场景必须执行 Stage 0 自检**：

1. **会话首个请求**：在收到用户首个请求后、输出任何实质性内容之前。
2. **延续轮次的新任务**：当用户在当前会话中提交一个**与上一轮任务明显不同**的新请求时（如上一轮生成博客、本轮要求排查报错），必须在输出前重新执行 S1-S5 自检，并按完整流水线阶段顺序执行。

> **判定标准**：如果用户的新请求涉及不同的任务类型（如从"内容创作"变为"问题排查"），或明确开启了新的工作项，则视为新任务，必须重新走完整流水线。如果用户的新请求是对上一轮任务的追问或补充（如"修改标题""添加一段内容"），可视为同一任务的延续，但仍需补全未执行的流水线阶段。

### 0.2 启动检查清单（Startup Checklist）

按顺序执行，**不可跳过任何一步**：

- [ ] **S1. 确认 AGENTS.md 已加载**：检查上下文中是否包含 AGENTS.md 的内容。若未加载，立即读取 `AGENTS.md`。
- [ ] **S2. 读取本文件**：确认已读取 `pipeline-executor.md` 的内容。若未读取，立即读取。
- [ ] **S3. 读取 pipeline-config.yml**：加载声明式流水线配置。若读取失败，记录原因并降级执行（见 0.4）。
- [ ] **S4. 读取 skills-registry.md**：加载 Skill 动态注册表，为后续 skill_match 阶段做准备。
- [ ] **S5. 检查日志文件**：确认 `.ai-pipeline.log` 存在。若不存在，执行 `touch .ai-pipeline.log` 创建并写入 Header：
  ```
  # AI Pipeline Log — DroneBlog
  # Format: [ISO8601] [STATUS] [STAGE] Message
  ```
- [ ] **S6. 状态就绪标记**：向用户展示 `[Pipeline Ready]` 标记（可在首次回复中隐含，不必单独发送）。

### 0.3 自检失败的处理

| 失败场景 | 处理方式 |
|---------|---------|
| S1/S2 失败（无法读取核心规范） | 在回复中声明 `[Pipeline] ⚠️ 无法加载核心规范文件，流水线部分功能受限`，然后继续尽力服务用户 |
| S3 失败（无法读取 pipeline-config.yml） | 降级为仅执行 AGENTS.md 中的「快速检查清单」，跳过流水线阶段标记和日志写入 |
| S4 失败（无法读取 skills-registry.md） | Skill 匹配阶段降级为「无动态匹配能力」，直接输出 `[Skill Match] 注册表不可用` 后继续 |
| S5 失败（无法创建日志文件） | 在回复中声明 `[Pipeline] ⚠️ 日志文件不可写`，后续所有 A 类动作改为在回复中显式声明 |

### 0.4 降级执行模式

当 pipeline-config.yml 不可用时，执行以下最小流程：

```
[ ] 1. 需求分析（基于 AGENTS.md 快速检查清单）
[ ] 2. 执行操作
[ ] 3. 构建验证（hexo clean && hexo generate，如适用）
[ ] 4. 安全审查（敏感信息检查 + .gitignore 确认）
```

> **自检规则**：如果 AI 意识到自己跳过了 S1-S5 中的任何一步，必须在该次回复中承认遗漏，并立即补执行。

### 0.5 延续轮次执行规范（Critical Fix）

**问题背景**：AI 在同一用户会话的延续轮次中，容易跳过流水线阶段直接进入执行动作，导致日志缺失、阶段标记未输出、compliance_audit/security 被绕过。

**强制规则**：

- **规则 R1**：每一轮用户消息都应被视为一个潜在的"新任务周期"起点。AI 必须在收到用户消息后、执行任何文件/命令操作前，快速判断：
  - 这是**同一任务的延续**（如追问、补充、修改）→ 可以复用已完成的阶段，但**必须补全未执行的后续阶段**
  - 这是**新任务**（如换了话题、新的工作项）→ **必须重新执行完整流水线**

- **规则 R2**：即使判定为"同一任务延续"，如果上一轮存在未执行的流水线阶段（如 compliance_audit、security、output），本轮**必须补执行这些阶段**，不得继续跳过。

- **规则 R3**：延续轮次中，如果上一轮已输出 `[OK] [output] 输出规范 completed`，则新一轮必须重新从 `analysis` 阶段开始。

- **规则 R4**：每轮回复结尾必须包含 `[Pipeline] 当前进度:` 进度条，即使该轮仅做了补正。

## 一、任务周期动作矩阵（Task-Cycle Action Matrix）

每当用户提交一个新任务，AI 必须按 `pipeline-config.yml` 中定义的 `stages` 顺序执行配套动作。

动作分为两类：
- **A 类（文件动作）**：必须调用 Shell 工具写入 `.ai-pipeline.log`
- **B 类（输出动作）**：必须在回复文本中显式输出阶段标记

### 1.0 阶段间信号机制（Stage Gate Protocol）—— 最高优先级规则

**核心原则**：任何阶段在执行前，必须验证上一阶段已发送合规完成信号。无信号 = 不得进入下一阶段。

#### 1.0.1 信号定义

每个阶段完成后，必须在 `.ai-pipeline.log` 中写入以下格式的信号：

```
[YYYY-MM-DDTHH:mm:ss+08:00] [OK] [{stage.id}] {stage.name} completed[: 附加信息]
```

#### 1.0.2 信号验证流程

进入每个阶段前，AI 必须执行以下检查：

1. **读取日志**：检查 `.ai-pipeline.log` 中是否存在上一阶段的 `[OK]` 信号
2. **信号存在**：正常进入当前阶段
3. **信号缺失**：
   - 立即标记为 **流程违规**
   - 写入日志：`[YYYY-MM-DDTHH:mm:ss+08:00] [FAIL] [{current_stage}] 流程违规: 上一阶段 {prev_stage} 未发送合规完成信号`
   - 进入 **compliance_audit 阶段**（流程合规审核）
   - **中止当前流水线**，从违规阶段开始重新执行

#### 1.0.3 重新执行规则

当 compliance_audit 检测到流程违规时：

1. 在回复中输出：
   ```
   [Pipeline] ⚠️ 流程合规审核检测到违规
   [Pipeline] 违规类型: {违规描述}
   [Pipeline] 违规阶段: {stage_name}
   [Pipeline] 正在从违规阶段重新执行...
   ```
2. 清除当前阶段的临时状态（如有）
3. 回到违规阶段，严格按照规范重新执行
4. 重新执行次数上限：`pipeline-config.yml` 中 `failure_policy.compliance_violation.max_re_execute`（默认 2 次）
5. 超过上限仍违规：输出 `[Pipeline] ❌ 流程合规无法恢复，建议人工介入`，终止任务

### 1.1 阶段执行模板

对于 `pipeline-config.yml` 中定义的每个 stage：

**阶段开始前——信号验证（强制）**：
```bash
# 1. 检查上一阶段信号
grep "\[OK\] \[{prev_stage_id}\]" .ai-pipeline.log | tail -1
# 2. 若结果为空，触发流程合规审核
```

**A 类动作（日志）**：
```bash
echo "[YYYY-MM-DDTHH:mm:ss+08:00] [START] [{stage.id}] Pipeline started for task: {简述}" >> .ai-pipeline.log
```

阶段成功完成后：
```bash
echo "[YYYY-MM-DDTHH:mm:ss+08:00] [OK] [{stage.id}] {stage.name} completed" >> .ai-pipeline.log
```

阶段失败时：
```bash
echo "[YYYY-MM-DDTHH:mm:ss+08:00] [FAIL] [{stage.id}] {stage.name} failed: {原因}" >> .ai-pipeline.log
```

> **时间戳格式强制规范**：必须使用 `[YYYY-MM-DDTHH:mm:ss+08:00]` 格式（单次 `+08:00`）。禁止出现 `+08:00+08:00` 等重复时区偏移。

**B 类动作（输出）**：
```
[Pipeline] 阶段 {n}/{total}: {stage.name} [ ] → [x]
```

### 1.2 子步骤追踪

执行阶段（execute）可能包含多个子步骤。AI 应在**每一轮回复结束时**更新子步骤状态：

```markdown
[Pipeline] 当前进度:
[x] 1. 需求分析 — {简述}
[x] 2. Skill 识别 — {结果}
[x] 3. 执行流程 — 子步骤 {m}/{n} 完成
[x] 4. 流程合规审核 — {结果}
[x] 5. 安全审查 — {结果}
[x] 6. 输出规范 — {结果}
```

> **规则**：如果某阶段被跳过（如 Skill 识别无匹配），用 `[x]` 标记但标注 `(跳过/无匹配)`。
> **新增规则**：compliance_audit（流程合规审核）阶段**不可跳过**，必须在执行阶段完成后、安全审查前执行。

### 1.3 内容创作子步骤详细规范（Content Creation Sub-steps）

当执行阶段触发 `content_creation` 子流程时，必须按以下顺序执行并验证：

#### 步骤 1：确认 Front-matter（validate_frontmatter）

**必检字段**：
- `title`：符合「{技术名} {内容类型}」格式，如 `C++ 核心特性深度解析`
- `date`：格式 `YYYY-MM-DD HH:mm:ss`

**选检字段规范**：
- `tags`：
  - 数量限制：**2-3 个**
  - 第1标签：核心技术/语言（如 `C++`, `React`, `Docker`）
  - 第2标签：主题方向（如 `并发编程`, `源码解析`, `性能优化`）
  - 第3标签（可选）：细分领域（如 `模板元编程`, `状态管理`, `容器编排`）
- `categories`：
  - 单一分类，**6 选 1**
  - 可选值：`后端开发` / `前端技术` / `系统编程` / `云原生` / `人工智能` / `分布式系统`

**违规处理**：
- 字段缺失 → 立即补全
- 格式不符 → 修正后重新校验
- 标签数量超限 → 精简至 2-3 个核心标签
- 分类不在白名单 → 按内容重新归类

#### 步骤 2：文件名规范检查（validate_filename）

**命名规则（kebab-case ASCII only）**：
```
{技术名缩写}-{内容主题}-{内容类型}.md
```

| 规则项 | 要求 | 示例 |
|--------|------|------|
| 大小写 | 全小写 | `cpp-core-features.md` |
| 连接符 | 短横线 `-` | `react-hooks-deep-dive.md` |
| 字符集 | ASCII 仅 | `kafka-message-transmission.md` |
| 禁止项 | 中文、空格、下划线、驼峰、无意义缩写 | ❌ `C++语言特性.md` ❌ `react_hooks_guide.md` |

**命名示例对照表**：
| 文章标题 | 正确文件名 |
|---------|-----------|
| C++ 核心特性深度解析 | `cpp-core-features.md` |
| React Hooks 深度解析 | `react-hooks-deep-dive.md` |
| Kafka 消息传输机制源码解析 | `kafka-message-transmission.md` |
| Docker 容器化实战入门 | `docker-containerization-practice.md` |
| AI Agent 工程化实践 | `ai-agent-engineering.md` |

**违规处理**：
- 文件名不符合规范 → 在写入前重命名为合规文件名
- 若文件已存在且需改名 → 使用 `mv` 命令重命名，并同步更新引用

#### 步骤 3：写入文件（write_file）

在确认 Front-matter 和文件名均合规后，执行文件写入：
- 目标目录：`source/_posts/`
- 文件编码：UTF-8
- 换行符：LF (`\n`)

#### 步骤 4：构建验证（build_verify）

```bash
hexo clean && hexo generate
```

- 构建成功 → 继续下一阶段
- 构建失败 → 检查 Front-matter 格式、文件名冲突、特殊字符等问题

## 二、失败与回滚触发器（Failure & Rollback Triggers）

### 2.1 失败计数器规则

AI 必须在**内存中维护当前任务的失败计数器**（按子任务维度）：

- 每次子任务失败 → 该子任务计数器 +1
- 同一子任务连续成功 → 计数器清零
- 不同子任务之间计数器**不累积**

### 2.2 自动回滚触发（≥3 次连续失败）

**触发条件**：同一子任务连续失败计数器 ≥ `pipeline-config.yml` 中 `failure_policy.max_retries`（默认 3）。

**强制动作序列**：

1. **A 类（日志）**：
   ```bash
   echo "[...] [ROLLBACK] [{子任务}] 连续失败≥3次，中止流水线。错误汇总: {简述}" >> .ai-pipeline.log
   ```

2. **B 类（输出）**：
   ```
   [Pipeline] ⚠️ 自动回滚触发
   [Pipeline] 阶段 3/5: 执行流程 [x] → [ROLLBACK]
   
   **错误总结**:
   - 第1次: {错误A}
   - 第2次: {错误B}
   - 第3次: {错误C}
   
   **建议**: 请人工检查环境或提供更明确的修复方向。
   ```

3. **终止后续操作**：不再继续执行该任务的后续阶段。

### 2.3 用户主动中断触发

**触发条件**：用户在任意 Checkpoint 输入 `stop` / `abort` / `取消`（定义见 `pipeline-config.yml` `failure_policy.abort_keywords`）。

**强制动作序列**：

1. **A 类（日志）**：
   ```bash
   echo "[...] [ABORT] [{当前阶段}] 用户输入 stop/abort/取消，任务中断" >> .ai-pipeline.log
   ```

2. **B 类（输出）**：
   ```
   [Pipeline] 🛑 用户中断
   [Pipeline] 任务已中止，不保存中间状态。
   ```

3. **终止**：立即停止，不执行任何收尾动作。

## 三、输出格式模板库（Output Template Library）

以下模板必须在对应阶段**原样输出**（可填充变量，不可省略结构）。

### T1. 阶段进度条（每轮回复必含）

```markdown
[Pipeline] 当前进度:
[x] 1. 需求分析 — {简述}
[x] 2. Skill 识别 — {结果}
[x] 3. 执行流程 — 子步骤 {m}/{n} 完成
[x] 4. 流程合规审核 — {结果}
[x] 5. 安全审查 — {结果}
[x] 6. 输出规范 — {结果}
```

> **规则**：
> - 如果某阶段被跳过（如 Skill 识别无匹配），用 `[x]` 标记但标注 `(跳过/无匹配)`
> - **compliance_audit（流程合规审核）阶段不可跳过**，必须始终执行

### T2. 文件操作确认（执行阶段子步骤）

```markdown
- [x] 写入: `{文件路径}` ({字节数} bytes)
- [x] 修改: `{文件路径}` ({替换次数} 处)
```

### T3. 命令执行结果（执行阶段子步骤）

```markdown
- [x] 执行: `{命令}`
  - 退出码: {code}
  - 输出: {stdout 摘要}
```

### T4. 最终汇报（输出规范阶段）

使用 `pipeline-config.yml` 中 `output_templates.default_report` 定义的章节：

```markdown
---

**修改摘要**: {简明说明}

**文件清单**:
| 操作 | 路径 |
|------|------|
| 新增 | {path} |
| 修改 | {path} |

**验证结果**: ✅ {简述} / ❌ {错误简述}

**Skill 匹配结果**: {匹配到的 skill 名称} / 无匹配

**已加载 Skill**: {skill-name} / 无

**后续建议**: {部署/调整/检查建议}
```

## 四、每轮回复后自检清单（Per-Reply Self-Check）

每完成一轮回复（即每次调用工具后向用户输出前），AI 必须自检以下 5 项：

- [ ] **C1. 阶段标记检查**：本轮回复是否包含了当前阶段的 `[Pipeline] 阶段 n/N: {name}` 标记？
- [ ] **C2. 日志写入检查**：如果本轮有文件操作或命令执行，是否已写入 `.ai-pipeline.log`？
- [ ] **C3. 进度条检查**：本轮回复结尾是否包含了 `[Pipeline] 当前进度:` 进度条？
- [ ] **C4. find-skills 强制触发检查**：如果当前任务处于 Skill 识别阶段且本地注册表未匹配，是否已执行 `npx skills find {关键词}`？（禁止主观跳过）
- [ ] **C5. 阶段间信号检查**：当前阶段开始前，是否验证了上一阶段的 `[OK]` 合规信号存在于 `.ai-pipeline.log` 中？

**自检结果处理**：

| 检查结果 | 处理方式 |
|---------|---------|
| 5 项全部通过 | 正常发送回复 |
| 有遗漏项 | 在回复开头追加 `[Pipeline] ⚠️ 自检发现遗漏: {遗漏项说明}`，然后补输出缺失内容 |
| 发现流程违规（如 C4/C5 失败） | 触发 **compliance_audit 阶段**，从违规阶段重新开始执行 |

## 五、冲突解决优先级

当本文件中的动作指令与其他规范冲突时，按以下优先级执行：

1. **最高**：用户直接指令（如用户说"不要写日志"）
2. **次高**：本文件中的动作指令（日志写入、阶段标记）
3. **中等**：`pipeline-config.yml` 中的声明式配置
4. **次低**：AGENTS.md 中的业务规范（安全审查、命名规范等）
5. **最低**：已加载 Skill 中的约束

> **例外**：如果用户明确说"跳过流水线"或"不用管 AGENTS.md"，则暂停本文件的所有动作指令。

## 六、自检与补正机制

### 6.1 自检触发

AI 在以下情况必须进行自检：
- 完成一轮回复后，意识到本轮未输出阶段标记
- 完成一轮回复后，意识到本轮未写入日志
- 用户质疑"为什么没有按照 AGENTS.md 执行"
- **任何阶段开始前，未检测到上一阶段的 `[OK]` 合规信号**
- **Skill 识别阶段未执行 find-skills 回退搜索（流程违规）**

### 6.2 补正动作

1. 在回复中承认遗漏：
   ```
   [Pipeline] ⚠️ 自检发现遗漏: 未执行 {动作名}
   ```
2. **判断是否为流程违规**：
   - **一般遗漏**（如漏写一条日志、漏输出一个标记）：立即补执行遗漏的动作，继续后续流程
   - **流程违规**（如跳过 find-skills、阶段信号缺失、未验证上一阶段信号）：
     1. 写入日志：`[FAIL] [{stage}] 流程违规 detected: {reason}. 触发重新执行。`
     2. 输出：`[Pipeline] ⚠️ 流程合规审核检测到违规，正在从违规阶段重新执行...`
     3. **中止当前流水线**
     4. 回到违规阶段，严格按照规范重新执行
     5. 重新执行时必须通过 **compliance_audit 阶段** 验证
3. 重新执行次数上限为 2 次，超过则终止任务并建议人工介入

## 八、流程合规审核阶段详细规范（Compliance Audit Stage）

### 8.1 执行时机

compliance_audit 阶段在执行阶段（execute）完成后、安全审查（security）之前执行。**任何情况下不可跳过**。

### 8.2 审核内容

1. **上一阶段信号验证**：
   - 检查 `.ai-pipeline.log` 中是否存在 `execute` 阶段的 `[OK]` 信号
   - 信号格式：`[OK] [execute] 执行流程 completed`

2. **历史违规扫描**：
   - 扫描日志中是否存在以下违规模式：
     - `流程违规`
     - `find-skills 回退搜索未执行`
     - `阶段标记未输出`
     - `日志未写入`
     - `未发送合规完成信号`

3. **跨阶段一致性检查**：
   - 检查所有已执行阶段是否都有对应的 `[START]` 和 `[OK]` 日志条目
   - 检查阶段顺序是否符合 pipeline-config.yml 定义

### 8.3 审核结果处理

| 审核结果 | 处理方式 |
|---------|---------|
| 全部合规 | 写入 `[OK] [compliance_audit] 流程合规审核 completed`，继续执行 security 阶段 |
| 发现违规 | 写入 `[FAIL] [compliance_audit] 流程违规 detected: {reason}`，触发重新执行 |

### 8.4 重新执行流程

1. 确定违规阶段（如 `skill_match` 未执行 find-skills）
2. 输出：`[Pipeline] ⚠️ 流程合规审核检测到违规，正在从 {stage_name} 阶段重新执行...`
3. 回到违规阶段，清空该阶段及之后的所有临时状态
4. 严格按照规范重新执行该阶段
5. 重新执行后再次进入 compliance_audit 验证
6. 重新执行次数上限：2 次
